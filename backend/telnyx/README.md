# Telnyx adapter boundary (provisional)

This folder is an **unintegrated adapter**, not a working product feature. It has no HTTP route, persistence, queue, provider API client, UI, infrastructure, or production configuration. Use only `verifyAndParseWebhook`, which authenticates the exact `Uint8Array` raw body and parses those same bytes before returning normalized data. It rejects invalid signatures before JSON parsing. The future caller must enforce request-size limits, atomically persist the event ID before acknowledging it, and apply safe out-of-order transitions.

Webhook verification follows Telnyx's documented `telnyx-signature-ed25519` and `telnyx-timestamp` headers: Ed25519 over the exact raw request bytes prefixed with `timestamp|`, using the account's base64-encoded signing public key. Freshness defaults to five minutes. Keys must come from trusted runtime configuration and be rotated per provider procedure. Do not bypass verification on missing configuration. Runtime support for WebCrypto Ed25519 must be verified in the eventual Worker deployment target.

Only the listed fax and voice event names are accepted; unknown types are rejected. Voice direction normalizes Telnyx's documented `incoming`/`outgoing` values but is optional because later event payloads may omit it. A voice event requires `call_control_id`; `call_session_id` is a separate correlation identifier and cannot replace it. Fax direction is required and uses `inbound`/`outbound`. `fax.received` is not evidence of delivery to a recipient and remains `unknown`. Status mapping is intentionally conservative and must be validated against event payloads and product transition rules.

Freshness checks are **not** durable deduplication. Event IDs must be stored with an atomic unique constraint/transaction in durable storage, retained for the provider retry/replay horizon (and any longer operational replay period), before acknowledging the webhook. This module only supplies the proposed key `telnyx:<event-id>`; it does not prevent duplicate processing. No fax send, receive routing, calling, voicemail, number provisioning, or account capability is enabled by this module. All capability flags default to false.

Tests use locally generated ephemeral Ed25519 keys and documented-shape synthetic payloads only. They do not contact Telnyx or perform paid operations. References: [Webhook fundamentals](https://developers.telnyx.com/docs/development/api-fundamentals/webhooks/receiving-webhooks.md), [Programmable Fax receiving webhooks](https://developers.telnyx.com/docs/programmable-fax/receiving-webhooks), [Voice API webhooks](https://developers.telnyx.com/docs/voice/programmable-voice/voice-api-webhooks.md).

## Voice projection foundation

`voice.ts` is a pure, unconnected call-leg projection and default-closed permission helper. It cannot make calls, issue credentials, ingest webhooks, or save recordings. A recording event means only that the provider reported a recording; it is not an archived or playable voicemail. Project only authenticated events after durable deduplication; the caller must store event IDs and update the projection atomically. Late or regressive lifecycle events cannot reopen a call. A voicemail permission requires both inbound voice and voicemail flags; these helpers alone are not enforcement at any operation boundary.

On 2026-11-17 a read-only Telnyx account lookup found the requested +12134587846 active with an assigned connection. This does not establish the connection type, WebRTC readiness, shared fax routing, emergency calling, or whether voicemail is configured; a voicemail settings lookup returned 404. No account or routing settings were changed. Telnyx's API catalog lists credential-token creation and recording APIs, but token lifetime/scope, safe session issuance, inbound delivery and recording retrieval need verification. Before enabling anything, implement Access-authenticated session issuance with verified short-lived least-privilege credentials, server-side operation gates, authenticated durable webhook intake, private recording archival and authorized playback, retention/consent controls, provider reconciliation, and account-specific routing and emergency-call validation. No master API credential may reach a client. Synthetic tests are not provider or deployment evidence.
