# Unified native product and release gaps

The intended product uses `com.justinharbour.simpledocs` for the main app on iOS/iPadOS, macOS and eventually tvOS. The current project builds only iOS/iPadOS and macOS, both connected to a self-hosted instance. A separate macOS direct preview is deliberately not shipped. Direct mode requires real provider adapters, explicit feature eligibility, review of data flows and confirmations, secure device-only Keychain storage and tests before enabling a choice or accepting credentials. Inbound delivery, voicemail, synchronization and push cannot be assumed without a backend. The existing Keychain service name is not itself an entitlement and does not guarantee access across changed app identities.

Apple's [App Store Connect documentation](https://developer.apple.com/help/app-store-connect/create-an-app-record/add-platforms/) supports adding macOS and tvOS to an iOS record with the same bundle ID, SKU and Apple ID. Platform builds and metadata remain platform-specific; this does not imply one binary. tvOS requires its own target, remote/focus UX, available API review, authentication and tests. Apple's [extension table](https://developer.apple.com/documentation/technologyoverviews/app-extensions) lists Share extensions on iOS/iPadOS and macOS, not tvOS. A future extension needs its own subordinate bundle identifier and appropriate provisioning; use app groups or Keychain sharing only if a reviewed design actually needs them. No shared entitlements are added here.

Apple's [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/) require data security (1.6), extension compliance (4.4), and transparency and permission for applicable data sharing (5.1). Apple's [2026 App Store Connect lab](https://developer.apple.com/videos/play/wwdc2026/8010/?time=1553) discusses user-supplied third-party keys and privacy, not a blanket approval of any implementation. Review provider terms and current guidelines, submit complete review access, and obtain Apple review for the actual app; no general approval is claimed. Do not embed developer-owned secret keys in app binaries.

Before release the owner must verify ownership and availability of the main App ID, configure the platform records, capabilities, signing and provisioning, and test actual signed platform builds. This change makes no Apple account changes. Bundle ID changes mean separate installs and may isolate preferences and Keychain data. Confirm OAuth callback allowlists and deploy the compatible Worker and database migration first; see [self-hosted instances](self-hosted-instances.md) and [push](push.md). Preserve old callback and APNs topic support during migration, validate real device registration separately, and do not claim a live cutover from unsigned builds.
