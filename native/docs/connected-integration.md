# Connected-instance integration foundation

Status: **foundation only.** `native/Packages/SimpleDocsConnected` is pure Swift logic with tests. It makes no network request, reads no Keychain, stores no token and is not linked into any app target. Native sign-in for self-deployed instances is **not verified**, so every credential decision in this package is a denial. Nothing here shows that an instance exists, that an address belongs to a trusted identity provider, or that any capability is available.

It follows the proposed architecture and integration contracts in PR #2 (`docs/architecture.md`, "Native capability boundary" and "Independently operated instances"; `docs/contracts.md`, "Instance onboarding and provisioning"). Those files are not on `develop` yet, so they are not linked. Both are proposals; this package implements only the client-side rules that do not depend on undecided items.

## What the package provides

| Type | Purpose |
| --- | --- |
| `InstanceOrigin` | Strict parser for a user-entered address. Accepts only `https://<dns-name>[:port]`, lowercased, with default port 443 normalised away. |
| `AcknowledgedOrigin` | An origin plus a caller-supplied acknowledgment string that must equal the canonical origin. A consistency check only: it is **not** evidence that a person saw or accepted the origin (see below). |
| `InstanceLinkID`, `SessionScope` | A device-local link identity and the names derived from it: Keychain account, cache directory components, idempotency namespace. Names only; no storage. IDs are generated by the registry; there is no public initializer. |
| `OriginBinding` | `permits(url, for: origin)` for requests and redirects; `apiURL(segments:)` builds `/api/v1/...` URLs from validated segments. |
| `InstanceRegistry` | In-memory linked instances, explicit selection, an epoch that changes on every switch, and unlink receipts. |
| `ContextBinding` | Pins a pending action to the link and epoch it started under. |
| `CredentialPolicy`, `NativeAuthStatus` | Gate for attaching a credential to a request. Fails closed. |
| `APIVersion` | Picks a supported major version or refuses. |
| `WorkerPlanner` | Inert plans for the current owner Worker's mail draft read/write and fax status read routes, bound to a selected link and epoch. No transport, credential, or authorization is provided. |

## Owner Worker contract foundation

`WorkerPlanner` models `/api/mail-drafts/{id}` GET/PUT and `/api/faxes/{id}` GET,
not the proposed `/api/v1` interface. Plans validate the Worker's UUID-v4,
draft revision, object JSON and 64 KiB request limit, and retain an instance
binding that becomes stale on switching or unlinking. Unknown fax statuses stay
unknown; acceptance is not delivery. Plans must not be logged: draft bodies may
contain private data. This does not establish that any instance supports the
owner Worker contract. There is deliberately no send or voice operation here.

Before a transport executes a plan it must revalidate the binding and the
credential policy, use verified instance-specific authentication, prevent
cross-origin redirects and shared cookie/cache leakage, and discard responses
whose binding became stale. These requirements are not implemented by an inert
plan. The Worker's mutation routes require an exact same-origin `Origin` header;
native compatibility must be verified rather than weakening the server check.
The actual server authenticates through Access today; supporting other instance
identity systems requires a separately reviewed server and native contract,
not an Entra requirement or automatic fallback.

## Cloudflare Access native authentication research (2026-11-17)

Cloudflare's [Managed OAuth documentation](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/managed-oauth/)
describes a user-based browser authorization-code flow for non-browser clients of
self-hosted Access applications. It requires Managed OAuth enabled on that
specific application and an RFC 8707-capable client. The documented discovery
endpoint is `https://<app-domain>/.well-known/oauth-authorization-server`.
Native custom-scheme callback URIs must be explicitly registered and match
exactly; localhost and loopback clients have separate settings. Access tokens are
opaque, and Access resolves them and forwards a signed assertion to the origin;
they are not JWTs for the client to decode or forward as origin assertions.
Cloudflare also documents access-token expiry and refresh-token grant duration.
This flow uses whichever identity provider the instance administrator configures;
it does not require Entra.

This is documentation evidence, not a verified Simpledocs integration. Managed
OAuth is not known to be enabled on any selected instance, and enabling it is an
operator-controlled infrastructure change outside this work. A secure client
still needs an instance-bound issuer/discovery trust design, registration and
callback ownership, authorization-code PKCE and state validation, resource
binding, token exchange, refresh/revocation semantics, Keychain isolation and
redirect restrictions, all tested end to end. Confirm the exact metadata,
registration, supported PKCE and resource behavior against the selected Access
application rather than inferring them from this overview. Review the worker's
same-origin mutation requirement for native clients without weakening it.

Cloudflare's [Access JWT validation documentation](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/)
describes the `Cf-Access-Jwt-Assertion` header as an assertion forwarded to the
origin, verified against that instance's configured issuer and application
audience. That is distinct from the OAuth client's opaque token. Neither is a
reason to accept an arbitrary identity issuer or embed an Access service token.

No credential-bearing transport or authentication implementation was enabled
on this evidence. The guard remains in force; `CredentialPolicy` denies every
request, and the app cannot connect. An operator-selected non-Cloudflare identity
mode would need its own reviewed contract, not a silent fallback.

## Address parsing

The parser does not rely on `URL` or `URLComponents` leniency. It rejects:

- non-HTTPS schemes, missing scheme, scheme-relative addresses
- user info, including `host@evil` confusions and backslashes
- any path other than a single `/`, any query or fragment
- non-ASCII or control characters (people must use the punycode form; punycode hosts are flagged by `hasPunycodeLabel` so the UI can display them prominently)
- IP literals in any form (dotted, decimal, hex, bracketed IPv6), single-label hosts, and `localhost`, `.local`, `.internal`, `.lan` and similar suffixes
- empty, over-long, hyphen-edged or non-LDH labels, trailing dots, percent escapes
- ports that are empty, zero-padded, signed, zero or above 65535

Rejecting IPs and local names is a deliberate product choice for an App Store client that talks to a Cloudflare-hosted instance. A person developing an instance locally cannot link it. A separate, explicit developer path would need its own review.

Format validity is **not** instance validity. No code path may describe a parsed origin as verified, discovered or trusted.

## Instance-bound session isolation

- A link has a random local `InstanceLinkID` generated inside `InstanceRegistry`. Callers cannot supply one: the ID type and `SessionScope` have no public initializer, and the deterministic `link(_:id:)` overload used by tests is internal. The registry also remembers every ID it has issued, so an ID is refused (`LinkError.linkIDReused`) if it is currently linked or was unlinked earlier, before any state changes. A link can therefore never replace an existing instance, including the active one, and the epoch cannot be bypassed.
- Re-linking the same origin after unlinking creates a new ID, so old state cannot be mistaken for the new link. The used-ID memory lives in the in-memory registry; a future persistence layer must keep it (or keep IDs unguessable and never user-supplied) across relaunch.
- `SessionScope` derives Keychain account, cache path and idempotency namespace from the SHA-256 of the canonical origin (port included) plus the link ID. The raw host is not used in names.
- Selection is explicit. Linking never selects. Every change of selection, and unlinking the selected instance, advances the epoch. A `ContextBinding` taken before a switch stays stale even if the person switches back, so a draft or submit cannot silently retarget another instance or revive after a round trip.
- Unlinking returns a receipt listing what the caller must purge (session material, cached records, idempotency keys, pending actions) and records `serverRevocation: .notAttempted`. Local removal is not evidence that the server ended the session.
- Idempotency keys, cached records and sessions are never shared across links.

## Origin confirmation is a UI responsibility

`AcknowledgedOrigin` cannot prove that a person confirmed anything: any code can pass the canonical string back. The UI layer must display the origin prominently (including the `hasPunycodeLabel` warning), obtain an explicit user action, and only then create the value. That UI step does not exist yet and needs its own tests. Nothing in this package should be cited as evidence of user consent.

## Credential policy (fail closed)

`NativeAuthStatus` has `unknown` and `unsupported` only; there is deliberately no `verified` case. Adding one is a reviewed change that must come with the verified flow. `CredentialPolicy.evaluate` returns a `CredentialDenial` and has no allow result today. The order is: no selection, stale context, origin mismatch, then authentication not verified. Redirects are checked on both the source and the destination and never get an exemption. Callers must not attach a bearer token, cookie or Access token on any denial, and must not fall back to an embedded service token or provider key.

## Not integrated or not verified

- **Not wired into the app.** No app target, `project.yml` entry or shared `SimpleDocsKit` source references this package. That is enforced, not just stated: see "CI gate" below.
- **No sign-in.** The Access/OAuth flow, issuer and audience binding, renewal and revocation are undecided (see PR #2 architecture). The package cannot authenticate anyone.
- **No discovery.** The discovery route, schema and its authenticity binding are undecided. `APIVersion.negotiate` only handles a list the caller supplies, and that list must be treated as untrusted. `InstanceTrust` has a single `userEnteredUnverified` state.
- **No networking.** No `URLSession`, TLS or certificate policy, redirect delegate, timeout, response-size limit, or error-envelope decoding. `OriginBinding` and `CredentialPolicy` are the checks a future transport must call; the transport itself is unwritten and unreviewed.
- **No persistence.** The registry is in memory. Keychain storage, cache purge, relaunch behaviour and account-switch UI do not exist. `SessionScope` only produces names.
- **IDN.** Non-ASCII hosts are rejected rather than converted. Whether to convert and how to warn about homograph look-alikes is unresolved; the punycode flag is a display aid only.
- **Same-origin only.** Cross-origin identity providers are expected for real sign-in. Allowing one requires an explicit, per-instance trusted-issuer design that does not exist, and this package would deny it today.
- **Duplicate detection** is by canonical origin only; two instances behind one host with different identity configuration are not modelled.
- **No cancellation of in-flight requests** on switch or unlink; the epoch lets a caller detect staleness but nothing enforces it.
- **Tests** ran with `swift test` on macOS under Xcode 27.2. The library compiled for generic iOS with `xcodebuild`, but iOS tests were not run, and the package was not compiled inside the Xcode app project.
- **API contract is a proposal.** `/api/v1` and the version list are not a deployed API.

## CI gate

The `native-connected` job in `.github/workflows/ci.yml` always runs (it does not use project detection, so a deleted package fails instead of being skipped) and `pr-gate` requires it to succeed; skipped, cancelled or missing counts as failure. It runs `ci/guard.sh`, then `swift test`, and fails unless Swift Testing reports a passing run of at least 30 tests (a run that finds no tests exits 0 otherwise).

`ci/guard.sh` fails the build if:

- the package, its sources or its tests are missing
- anything under `native/` outside the package and `native/docs` mentions `SimpleDocsConnected` (so linking it into an app or `project.yml` needs a reviewed change to the guard)
- `Package.swift` declares a dependency
- sources use `URLSession`, `URLRequest`, `Network`, `Security`/`SecItem`, `AuthenticationServices`, `WebKit` or similar
- a `verified`, `trusted`, `authenticated` or `signedIn` case is added

The guard is a text search. It deters accidental drift and forces review; it is not a security proof, and a determined change to the package and the guard in the same PR is still possible, so code owners should review `ci/` and the workflow. Raising the test floor as tests are added is manual.

PR #11 also edits `ci.yml` (adds `native-direct`). The `native-connected` job sits after `native-apps` to limit overlap, but both PRs change the `pr-gate` `needs:` line, so whichever merges second must resolve that one-line conflict by listing both jobs.
