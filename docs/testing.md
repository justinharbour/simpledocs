# Integration and security test plan

**Status: planning.** Nothing in this document is a verified capability. This file defines the integration scenarios, pass/fail criteria and test fixtures that future implementation must satisfy. It is written against the proposed contracts in [the architecture](architecture.md) and [the integration contract](contracts.md) (PR #2, not yet merged to `develop`), [the provider feasibility notes](provider-feasibility.md) (PR #3, not yet merged), and [the implementation plan](plan.md).

## Test levels and tooling

These are the intended tools. Nothing here is wired into CI, and none of it is required for the current `pr-gate`.

| Level | Scope | Tooling (intended) | Runs against |
| --- | --- | --- | --- |
| U: unit | Pure domain logic: state transitions, hashing, canonical serialization, outcome derivation | Vitest (web/shared TS) or Swift Testing (native) | No network |
| A: API integration | Worker routes with D1 and R2 emulation, Access assertions faked, provider clients replaced by fakes | Worker test harness with local D1/R2 bindings (to be chosen) | Local only |
| W: webhook integration | Raw-byte signature verification, durable inbox, dedupe, reordering | Same harness, with fixtures generated by the test | Local only |
| P: provider sandbox | Real Telnyx test numbers and PostGrid test keys | Manual or scheduled, explicit owner authorization | Provider test environments only, never live |
| N: native pairing | Origin entry, discovery binding, Keychain scoping | XCTest/Swift Testing plus a local fake instance | Local fake instance |
| D: deployment | Fresh-account provisioning dry run | OpenTofu plan plus a throwaway Cloudflare account | Throwaway account only |

Rules that apply to every level:

1. No test may call a live provider endpoint or use a live credential. Provider tests use test keys and test numbers only.
2. No test may send a real message, fax, call or letter. PostGrid test orders do not mail; treat any non-test-key request as a failure.
3. Fixtures are synthetic (see [Fixtures](#synthetic-fixtures)). Real phone numbers, addresses, documents, provider payloads and credentials must not appear in tests, logs or PR text.
4. A test that needs a secret reads it from the local test environment only. Secrets are never committed, never printed, and never placed in a fixture file.

## Synthetic fixtures

| Fixture | Rule | Example |
| --- | --- | --- |
| Phone numbers | NANP fictional range, `+1 555 01XX XXXX`. The foundation's `SyntheticData` already uses `555 01`. | `+1 555 0100 01` |
| Postal addresses | Clearly fictional street and an example locality; no real addresses. | `100 Example Street, Testville, ZZ 00000` |
| Documents | Generated one-page PDF whose text is `SYNTHETIC TEST DOCUMENT <fixture-id>`. Stored under `fixtures/` with a content hash in the test. | `fixtures/doc-one-page.pdf` |
| Job titles | Must contain `Sample`, so tests can reject real content. | `Sample fax, partial success` |
| Provider webhook bodies | Generated by the test from a template, with fake IDs (`evt_test_0001`). Never copied from provider docs or a real account. | Built at test time |
| Signing secrets | Random per test run, held only in memory. Never a provider's secret. | `WEBHOOK_TEST_SECRET` from env |
| Access assertions | Generated by a fake issuer in the test, with a test audience and test key. | Built at test time |
| Provider test keys | Only the provider's documented test-key format, supplied locally. Never in the repo. | Local `.env` (gitignored) |

A fixture file is "real" if it contains a number, address, document or payload that could identify a person or organization. Any such file fails review.

## Scenario catalogue

Each scenario lists its preconditions, steps, and pass/fail criteria. "Expect" lines are assertions. Route names come from the proposed contract (PR #2). If a route changes there, update the scenario in the same change.

### S1. Access and authorization (A, Planned)

Preconditions: Worker running locally; fake Access issuer; flags default off.

| # | Step | Pass | Fail |
| --- | --- | --- | --- |
| S1.1 | `GET /api/v1/jobs/{id}` with no Access assertion | 401, error envelope, no job data | Any 200 or job field |
| S1.2 | Same request with an assertion for a wrong audience | 401 | Accepted |
| S1.3 | Same request with an expired assertion | 401 | Accepted |
| S1.4 | Valid assertion, actor lacks the operation's role | 403 | 200, or any data |
| S1.5 | Valid assertion, actor may read job X, requests job Y owned by another actor | 404 (does not reveal existence) | 403 or 200 that discloses Y |
| S1.6 | `POST /api/v1/jobs` with a client-supplied `createdBy` | Field ignored or rejected; stored actor equals the authenticated actor | Stored actor is the client value |
| S1.7 | Assertion present but CORS origin is foreign | Response has no CORS grant; a cross-origin cookie-authenticated mutation is rejected | Mutation succeeds |

Verification note: The Access validation rules (issuer, audience, signature, expiry, identity) are proposed. S1 cannot be signed off until the Access configuration is verified against Cloudflare Access documentation. Until then, every sensitive route must return 403 or 503 with feature disabled.

| # | Step | Pass | Fail |

| S3.2 | Enable `mail.outbound` via admin route without an admin actor | Rejected (403) | Accepted |

### S4. Job model, revisions and optimistic concurrency (A, Planned)

| # | Step | Pass | Fail |

### S5. Proof and approval gate for paid mail (A, Planned; P, Blocked)

Owner clarification: a local programmatic review is acceptable; provider-generated pre-send proof is not required. Ordinary PostGrid previews are generated after order creation. The foundation uses a revision-bound review of exact inputs and discloses rendering differences; a usable review UI and production validation remain outstanding. The historical S5 proof cases below describe the former proof design and are not claims about the implemented API.

| # | Step | Pass | Fail |
| --- | --- | --- | --- |
| S5.1 | Submit a mail delivery with no approval | Rejected (409 or 403); the fake PostGrid client records **zero** create calls | Any create call |
| S5.2 | Request a proof | Proof record created with `inputHash` and `proofHash`; fake records **zero** order creations | Any order creation during proof generation |
| S5.3 | Approve a proof whose `proofHash` does not match the delivery's current proof | Rejected (409) | Accepted |
| S5.4 | Approve the current proof, then change the recipient, then submit | Submit rejected; approval invalidated | Submit proceeds |
| S5.5 | Approve and submit with matching hashes and `mail.outbound` on | One create call with the approved inputs; the request body equals the canonical input hashed in the approval | Body differs in any field, or more than one create call |
| S5.6 | Proof source is the ordinary post-order preview, not a pre-send proof | Gate treats it as unsupported and blocks live submit | Live submit proceeds |
| S5.7 | Fake PostGrid returns the mail's `proof` URL before submit | No live order; the URL is stored as a proof artifact only if the proof path is verified | Treated as acceptance |

S5.5 and S5.6 can run without provider access, using a fake whose behaviour is defined by the contract. S5 is **Blocked** for real use until the provider's proof behaviour is verified.

### S6. Idempotency and paid-action safety (A, Planned)

Contract basis: PR #2 "State, retries and idempotency". Every submit must carry an `Idempotency-Key`. Each channel is tested separately.

| # | Step | Pass | Fail |
| --- | --- | --- | --- |
| S6.1 | Submit with key K and body B; retry with K and B | Second call returns the stored result; fake records **one** provider call | Two provider calls |
| S6.2 | Submit with key K and body B; retry with K and body B' | 409 with a fingerprint-mismatch error; no provider call | Accepted, or a provider call |
| S6.3 | Ten concurrent submits, distinct keys, same delivery revision | Exactly one provider call; nine get "already submitted" or "in progress" | More than one call |
| S6.4 | Key K reused by a different authenticated actor | Rejected; scoped keys do not collide across actors | Returns the other actor's result |
| S6.5 | Fake provider times out after receiving the request | Delivery state `unknown`; no automatic resend; a reconciliation task is created | Second provider call, or state `failed` |
| S6.6 | Worker crashes after reserving the key but before calling the provider | On restart, the reserved intent is reconciled; no duplicate call | Duplicate call |
| S6.7 | Resubmit after `unknown` | Blocked until reconciliation resolves the state; if it resolves to `delivered`, no resend | Resend while unresolved |
| S6.8 | A `fax` submit succeeds and a `mail` submit fails in the same job | Job outcome is `partial`; mail retry does not re-send the fax | Fax re-sent, or job reported as success |

Provider idempotency: whether a provider accepts a per-delivery key is unverified. Where it is not documented, the test asserts only the local rules above and the reconciliation path, not provider-side dedupe.

### S7. Webhook ingestion (W, Planned; Blocked for each provider)

Contract basis: PR #2 "Webhooks". Each provider's test must be written only after that provider's signature scheme is confirmed in its current documentation (PR #3 lists Telnyx and PostGrid as unverified). The steps below are provider-independent.

| # | Step | Pass | Fail |
| --- | --- | --- | --- |
| S7.1 | Valid signature over raw bytes | 2xx **after** the event row is durably written to the inbox | 2xx before write, or no write |
| S7.2 | Signature computed over a re-serialized body (reordered keys, changed whitespace) | Rejected (4xx); nothing persisted | Accepted |
| S7.3 | Tampered body with the original signature | Rejected; nothing persisted | Accepted |
| S7.4 | Timestamp outside the provider's freshness window (if the provider signs one) | Rejected | Accepted |
| S7.5 | Same verified event delivered twice | One inbox row; one side effect; second call returns 2xx without re-applying | Second side effect |
| S7.6 | Events delivered out of order (`completed` before `queued`) | No state regression; final state reflects the latest valid status; raw statuses retained | Regression to an earlier status |
| S7.7 | Inbox write fails (fault injection) | Non-2xx; provider will retry | 2xx |
| S7.8 | Request body over the size cap | Rejected before parsing | Parsed |
| S7.9 | Webhook route with an Access assertion but no provider signature | Rejected | Accepted |
| S7.10 | Signing key rotated: old key valid during overlap, new key valid | Both accepted during overlap; only new accepted after | Either wrong |

S7.5 and S7.6 use the duplicate and reordering model from the contract. "Expect" for S7.6 requires a status map from the provider documentation. Until that map exists, the test asserts only "no regression" in the local state machine.

### S13. Provider signature fixtures (W, Blocked)

Before a provider integration is accepted, its webhook scheme must be confirmed from the provider's current documentation. Then the fixture generator is written. Specifically:

1. Record the verified facts in this document (signed fields, algorithm, header name, timestamp rule, replay window) with the source URL and the date checked. Do not infer them from sample payloads.
2. Generate test vectors locally with a random test secret. Vectors must not reuse any provider sample secret.
3. Run S7.1 to S7.10 against the vectors.
4. Confirm the test fails if the verifier skips the raw-bytes rule (mutation test: parse and re-serialize before verifying; expect S7.2 to fail).

Pass: all of S7 pass against provider-specific vectors and the mutation test fails as expected. Until the source facts are recorded, S13 is not started.

### S14. Paid and live provider actions (P, Blocked; policy)

Paid or live provider actions are never routine tests. This follows PR #3 ("No live provider action during feasibility or routine tests") and the plan.

| # | Rule | Pass | Fail |
| --- | --- | --- | --- |
| S14.1 | Test configuration accepts only provider test keys and test numbers | Startup check refuses a live key | Live key accepted |
| S14.2 | Live provider action requires an explicit, named owner authorization recorded in the PR or change record | Authorization exists before the run | Run without it |
| S14.3 | Mail: a live run requires S5 to pass and a verified pre-send proof path | Both verified | Run proceeds without them |
| S14.4 | Fax and voice: a live run requires the Telnyx shared-number and routing checks from PR #3 | Checks recorded | Run proceeds without them |
| S14.5 | Any unexpected billable call during a test run | Test fails; the run stops and reports the call | Run continues |

## Pass/fail for the whole plan

The plan is satisfied for an implementation when:

1. Every scenario marked Planned in this document has a merged test, or an explicit recorded deferral with an owner.
2. No scenario marked Blocked has been run against a live provider or a live account.
3. The `Status legend` table is updated in the same change that merges a test. No row may move to "Implemented" without a test on `develop`.
4. CI is unchanged by this document. Wiring tests into CI is a separate, reviewed change under the repository's CI rules.

A run of this plan fails if any single scenario fails, is skipped without a recorded reason, or produces a live provider call. A passing unit test does not satisfy an integration scenario.
