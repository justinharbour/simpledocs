# Voice event and recording intake

The Worker accepts Telnyx signed POSTs at `/api/webhooks/telnyx/voice`. This endpoint is outside the Worker's Access JWT check; it authenticates the exact request bytes with the configured Telnyx Ed25519 public key and a five-minute timestamp window, and requires the configured connection ID. Telnyx must also be able to reach this path through any upstream Cloudflare Access policy: a narrowly scoped bypass for this path is necessary, while the remaining application and recording endpoints must stay Access-protected. Do not change Access or provider routing without review.

Before a reviewed deployment, apply `0006_voice_webhooks.sql` with the existing D1 migration procedure, provision a private R2 bucket and bind it as `VOICE_RECORDINGS`, and configure `TELNYX_PUBLIC_KEY` and `TELNYX_VOICE_CONNECTION_ID` through the deployment's secure configuration. No bucket or binding is provisioned by this change. Confirm the actual voice connection and signing key before configuring the endpoint. Intake remains unavailable when configuration is absent. Do not put a public bucket route on the recording bucket.

Authenticated events are inserted before acknowledgement; event IDs are unique. A recording-saved event archives audio into R2 and only then inserts a recording record and acknowledges. A failure returns 503 for provider retry. If the R2 write succeeds but the database write fails, a retry rewrites the same event-specific object key; orphan cleanup needs an operational policy. Lifecycle events are retained even when voice flags are off to reconcile existing calls. Recording consent, retention, deletion, storage limits, event retention, and an archival recovery process must be established before production use.

## Direct-to-voicemail call control

The separately gated voicemail flow is designed for a dedicated Telnyx **Call Control application**, not an existing WebRTC credential connection. With `VOICE_INBOUND_ENABLED=true`, `VOICEMAIL_ENABLED=true`, a private R2 binding, `TELNYX_API_TOKEN`, a configured E.164 `VOICEMAIL_NUMBER` and nonempty `VOICEMAIL_GREETING` (up to 1000 plain-text characters), a signed incoming `call.initiated` for that exact number is claimed in D1, then answered. After the matching `call.answered`, Telnyx speaks the configured greeting; after `call.speak.ended`, it starts a single-channel MP3 recording with a beep and a 120-second maximum. Configure a greeting that provides any required recording notice. The `call.recording.saved` webhook then archives the audio through the private storage flow. The feature is off unless both gates are explicitly true. No command is issued for other numbers or outgoing calls.

This immediately answers eligible calls; it does **not** ring a softphone first, detect missed calls, or provide an unattended fallback for an existing credential connection. A dedicated provider routing design and sandbox validation are prerequisites; never enable this on a connection shared with another call handler. Commands have a durable per-leg, per-action claim and a unique Telnyx `command_id`. A network failure or process failure after claiming produces an unknown outcome and is not retried automatically; this avoids repeating a potentially chargeable or disruptive action but may leave a call without a greeting or recording. Telnyx event arrival can race a hangup; provider rejection and out-of-order events must be monitored. Operators must reconcile unknown commands. Disabling flags stops new commands, not already accepted actions. There is no automatic hangup at the recording limit; provider recording `max_length` stops the recording, not necessarily the call. An external call-duration limit and operational monitoring are required before enabling.

Classification uses the server-generated per-call marker passed as Telnyx `client_state` on the record-start command and a durable record-start claim for that same call leg. A matching signed recording-saved event is labelled `voicemail`; other recordings stay `recording`. This is evidence of our voicemail recording command, not a claim that speech was actually left. Telnyx documents `client_state` as propagated to subsequent webhooks; test its precise propagation and speak-ended behavior in the target account before cutover. An out-of-order or missing marker remains a generic recording. No live routing or account changes were made.

The documented Telnyx-managed `https://s3.amazonaws.com/telephony-recorder-prod/` location is the only accepted source; redirects are refused and no API credential is sent to the URL. Custom storage and different Telnyx URL formats fail closed. Telnyx says these links expire in ten minutes, so sustained outages may require manual provider reconciliation and can cause missing audio. Signed URLs and raw payloads are not stored. Archived recordings can be listed at `GET /api/voice/recordings` and played at `GET /api/voice/recordings/{recording_id}`, both behind the existing Access JWT boundary and the configured `VOICE_OWNER_SUBJECT`, with no-store responses. This is a single-owner deployment, not tenant isolation. Listing is limited to 100 most recently archived recordings. No deletion endpoint is supplied.

## Browser credentials research

Telnyx recommends a per-device telephony credential under a Credential Connection and a backend-issued JWT passed to the JavaScript SDK as `login_token`. Its [authentication architecture](https://developers.telnyx.com/docs/development/webrtc/js-sdk/explanation/authentication-architecture) says JWTs expire after 24 hours or earlier when the parent credential expires, and the SDK emits warning 34001. The installed SDK's public types do not expose the documented `updateToken` method, so the UI asks the user to reconnect instead of pretending refresh works. No API key or SIP password is delivered to the browser.

The default-disabled session endpoint uses [POST /telephony_credentials/{id}/token](https://developers.telnyx.com/api-reference/access-tokens/create-an-access-token), with an operator-configured credential, caller number and Access subject. Set `VOICE_WEBRTC_ENABLED=true`, `VOICE_OWNER_SUBJECT`, `TELNYX_WEBRTC_CREDENTIAL_ID`, `TELNYX_VOICE_FROM`, and the secret `TELNYX_API_TOKEN` only after review. The credential must be dedicated to this owner/device and its provider-side capabilities, expiry, revocation, outbound destinations, billing limits, number routing, emergency behavior and shared fax behavior must be verified. Never grant an untrusted user access to the bearer: the browser can use it directly with Telnyx, bypass UI restrictions and potentially incur charges. Disabling issuance does not revoke already-issued tokens or terminate calls; revoke the provider credential if necessary. These environment switches are not independent inbound/outbound feature enforcement. No credentials were created and no live calls were made.

Telnyx documents [answer](https://developers.telnyx.com/api-reference/call-commands/answer-call), [speak](https://developers.telnyx.com/api-reference/call-commands/speak-text), and [record-start](https://developers.telnyx.com/api-reference/call-commands/recording-start) as distinct Call Control operations. A WebRTC Credential Connection alone does not prove the necessary Call Control ownership or unanswered-call routing. The direct-to-voicemail flow is not enabled by default and requires a separate reviewed provider setup.
