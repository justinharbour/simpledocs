# Voice event and recording intake

The Worker accepts Telnyx signed POSTs at `/api/webhooks/telnyx/voice`. This endpoint is outside the Worker's Access JWT check; it authenticates the exact request bytes with the configured Telnyx Ed25519 public key and a five-minute timestamp window, and requires the configured connection ID. Telnyx must also be able to reach this path through any upstream Cloudflare Access policy: a narrowly scoped bypass for this path is necessary, while the remaining application and recording endpoints must stay Access-protected. Do not change Access or provider routing without review.

Before a reviewed deployment, apply `0008_voice_webhooks.sql` with the existing D1 migration procedure, after the coordinated mail `0004`–`0006` and fax `0007` migrations are merged and applied. Verify the migration ledger and actual filenames before applying; the current base branch does not yet contain those pending migrations. Provision a private R2 bucket and bind it as `FILES`, and configure `TELNYX_PUBLIC_KEY` and `TELNYX_VOICE_CONNECTION_ID` through the deployment's secure configuration. No bucket or binding is provisioned by this change. Confirm the actual voice connection and signing key before configuring the endpoint. Intake remains unavailable when configuration is absent. Do not put a public bucket route on the recording bucket.

Authenticated events are inserted before acknowledgement; event IDs are unique. A recording-saved event archives audio into R2 and only then inserts a recording record and acknowledges. A failure returns 503 for provider retry. If the R2 write succeeds but the database write fails, a retry rewrites the same event-specific object key; orphan cleanup needs an operational policy. Lifecycle events are retained even when voice flags are off to reconcile existing calls. Recording consent, retention, deletion, storage limits, event retention, and an archival recovery process must be established before production use.

## Direct-to-voicemail call control

The separately gated voicemail flow is designed for a dedicated Telnyx **Call Control application**, not an existing WebRTC credential connection. With `VOICE_INBOUND_ENABLED=true`, `VOICEMAIL_ENABLED=true`, a private R2 binding, `TELNYX_API_TOKEN`, a configured E.164 `VOICEMAIL_NUMBER` and a greeting (up to 1000 plain-text characters), a signed incoming `call.initiated` for that exact number is claimed in D1, then answered. After the matching `call.answered`, Telnyx speaks the greeting; after `call.speak.ended`, it starts a single-channel MP3 recording with a beep and a 120-second maximum. Configure a greeting that provides any required recording notice. The `call.recording.saved` webhook then archives the audio through the private storage flow. The feature is off unless both gates are explicitly true. No command is issued for other numbers or outgoing calls.

The greeting and voice are read from the D1 `settings` table (`voicemail_greeting`, `voicemail_voice`, `voicemail_service_level`) when the call is answered, so a change on the Settings page applies to the next inbound call without a deploy. If no greeting is stored, `VOICEMAIL_GREETING` is the fallback; with neither, no command is issued. The default voice is `Telnyx.KokoroTTS.af`. A voice is either a `<Provider>.<Model>.<VoiceId>` name or the legacy `female`/`male`. Per the Telnyx speak docs, `service_level` (`basic` or `premium`) selects the quality of the legacy voices only, so it is sent only with `female` or `male` and omitted for named voices. The greeting is always sent as plain text.

When the browser softphone is online, the call rings it first (see below). With no softphone online it answers eligible calls immediately. It does not provide an unattended fallback for an existing credential connection. A dedicated provider routing design and sandbox validation are prerequisites; never enable this on a connection shared with another call handler. Commands have a durable per-leg, per-action claim and a unique Telnyx `command_id`. A network failure or process failure after claiming produces an unknown outcome and is not retried automatically; this avoids repeating a potentially chargeable or disruptive action but may leave a call without a greeting or recording. Telnyx event arrival can race a hangup; provider rejection and out-of-order events must be monitored. Operators must reconcile unknown commands. Disabling flags stops new commands, not already accepted actions. There is no automatic hangup at the recording limit; provider recording `max_length` stops the recording, not necessarily the call. An external call-duration limit and operational monitoring are required before enabling.

Classification uses the server-generated per-call marker passed as Telnyx `client_state` on the record-start command and a durable record-start claim for that same call leg. A matching signed recording-saved event is labelled `voicemail`; other recordings stay `recording`. This is evidence of our voicemail recording command, not a claim that speech was actually left. Telnyx documents `client_state` as propagated to subsequent webhooks; test its precise propagation and speak-ended behavior in the target account before cutover. An out-of-order or missing marker remains a generic recording. No live routing or account changes were made.

The documented Telnyx-managed `https://s3.amazonaws.com/telephony-recorder-prod/` location is the only accepted source; redirects are refused and no API credential is sent to the URL. Custom storage and different Telnyx URL formats fail closed. Telnyx says these links expire in ten minutes, so sustained outages may require manual provider reconciliation and can cause missing audio. Signed URLs and raw payloads are not stored. Archived recordings can be listed at `GET /api/voice/recordings` and played at `GET /api/voice/recordings/{recording_id}`, both behind the existing Access JWT boundary and the configured `VOICE_OWNER_SUBJECT`, with no-store responses. This is a single-owner deployment, not tenant isolation. Listing is limited to 100 most recently archived recordings. No deletion endpoint is supplied.

## Browser credentials research

Telnyx recommends a per-device telephony credential under a Credential Connection and a backend-issued JWT passed to the JavaScript SDK as `login_token`. Its [authentication architecture](https://developers.telnyx.com/docs/development/webrtc/js-sdk/explanation/authentication-architecture) says JWTs expire after 24 hours or earlier when the parent credential expires, and the SDK emits warning 34001. The installed SDK's public types do not expose the documented `updateToken` method, so the UI asks the user to reconnect instead of pretending refresh works. No API key or SIP password is delivered to the browser.

The default-disabled session endpoint uses [POST /telephony_credentials/{id}/token](https://developers.telnyx.com/api-reference/access-tokens/create-an-access-token), with an operator-configured credential, caller number and Access subject. Set `VOICE_WEBRTC_ENABLED=true`, `VOICE_OWNER_SUBJECT`, `TELNYX_WEBRTC_CREDENTIAL_ID`, `TELNYX_VOICE_FROM`, and the secret `TELNYX_API_TOKEN` only after review. The credential must be dedicated to this owner/device and its provider-side capabilities, expiry, revocation, outbound destinations, billing limits, number routing, emergency behavior and shared fax behavior must be verified. Never grant an untrusted user access to the bearer: the browser can use it directly with Telnyx, bypass UI restrictions and potentially incur charges. Disabling issuance does not revoke already-issued tokens or terminate calls; revoke the provider credential if necessary. These environment switches are not independent inbound/outbound feature enforcement. No credentials were created and no live calls were made.

Telnyx documents [answer](https://developers.telnyx.com/api-reference/call-commands/answer-call), [speak](https://developers.telnyx.com/api-reference/call-commands/speak-text), and [record-start](https://developers.telnyx.com/api-reference/call-commands/recording-start) as distinct Call Control operations. A WebRTC Credential Connection alone does not prove the necessary Call Control ownership or unanswered-call routing. The direct-to-voicemail flow is not enabled by default and requires a separate reviewed provider setup.

## Ring the softphone, then voicemail

The Calls page posts `POST /api/voice/presence` about every 30 seconds while connected and `{online:false}` when it closes. The Worker treats the phone as online for 90 seconds after the last beat (settings key `phone_online`).

On `call.initiated` for `VOICEMAIL_NUMBER`, if the phone is online and `TELNYX_WEBRTC_CREDENTIAL_ID` is set, the Worker claims a `voicemail_rings` row, reads the credential's `sip_username` (`GET /v2/telephony_credentials/{id}`) and sends `transfer` on the still-unanswered call to `sip:<sip_username>@sip.telnyx.com` with `timeout_secs: 20`, the caller as `from`, and `target_leg_client_state` set to a marker. Events for that softphone leg carry the marker and are not written to the call log. If its `call.hangup` arrives without a `call.answered` (timeout, decline, cancel), the Worker answers the original call and the greeting and recording flow continues. If the softphone answers, the original call is logged as answered and no voicemail starts.

A rejected transfer or failed credential lookup answers voicemail immediately. A transfer whose outcome is unknown waits and is not retried. This path has been tested only against fake Telnyx responses. The Call Control application must send events for the voice number's calls to the voice webhook, and the softphone leg's events must pass the `connection_id` check; if Telnyx reports another connection id for that leg, its hangup is rejected with 400 and a caller who is not answered gets no voicemail until the call ends.

## SMS

`POST /api/webhooks/telnyx/messaging` receives `message.received`, `message.sent` and `message.finalized`, verified with `TELNYX_PUBLIC_KEY` and bypassed in Access like the voice webhook. Messages are stored in `sms_messages` (migration `0014_sms.sql`) keyed by the Telnyx message id, so a redelivery changes nothing. Return 2xx quickly; Telnyx retries slow responses. Routes `/api/sms/*` and `/api/inbox*` are documented in `web/worker/README.md`.
