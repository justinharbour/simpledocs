# Voice event and recording intake

The Worker accepts Telnyx signed POSTs at `/api/webhooks/telnyx/voice`. This endpoint is outside the Worker's Access JWT check; it authenticates the exact request bytes with the configured Telnyx Ed25519 public key and a five-minute timestamp window, and requires the configured connection ID. Telnyx must also be able to reach this path through any upstream Cloudflare Access policy: a narrowly scoped bypass for this path is necessary, while the remaining application and recording endpoints must stay Access-protected. Do not change Access or provider routing without review.

Before a reviewed deployment, apply `0004_voice_webhooks.sql` with the existing D1 migration procedure, provision a private R2 bucket and bind it as `VOICE_RECORDINGS`, and configure `TELNYX_PUBLIC_KEY` and `TELNYX_VOICE_CONNECTION_ID` through the deployment's secure configuration. No bucket or binding is provisioned by this change. Confirm the actual voice connection and signing key before configuring the endpoint. Intake remains unavailable when configuration is absent. Do not put a public bucket route on the recording bucket.

Authenticated events are inserted before acknowledgement; event IDs are unique. A recording-saved event archives audio into R2 and only then inserts a recording record and acknowledges. A failure returns 503 for provider retry. If the R2 write succeeds but the database write fails, a retry rewrites the same event-specific object key; orphan cleanup needs an operational policy. Lifecycle events are retained even when voice flags are off to reconcile existing calls. The intake doesn't answer calls, initiate voicemail, or distinguish voicemail from other call recordings: **all recordings arriving from the configured connection are archived as recordings, not labelled as voicemail**. Recording consent, retention, deletion, storage limits, event retention, and an archival recovery process must be established before production use.

The documented Telnyx-managed `https://s3.amazonaws.com/telephony-recorder-prod/` location is the only accepted source; redirects are refused and no API credential is sent to the URL. Custom storage and different Telnyx URL formats fail closed. Telnyx says these links expire in ten minutes, so sustained outages may require manual provider reconciliation and can cause missing audio. Signed URLs and raw payloads are not stored. Archived recordings can be listed at `GET /api/voice/recordings` and played at `GET /api/voice/recordings/{recording_id}`, both behind the existing Access JWT boundary with no-store responses. The current owner application treats any Access-authorized actor as an owner; this is not tenant isolation. Listing is limited to 100 most recently archived recordings. No UI or deletion endpoint is supplied.

## Browser credentials research

Telnyx recommends a per-device telephony credential under a Credential Connection and a backend-issued JWT passed to the JavaScript SDK as `login_token`. Its [authentication architecture](https://developers.telnyx.com/docs/development/webrtc/js-sdk/explanation/authentication-architecture) says JWTs expire after 24 hours or earlier when the parent credential expires, and the SDK emits warning 34001 for refresh. Long-lived SIP passwords and the Telnyx API key should not be exposed to the browser. The [quickstart](https://developers.telnyx.com/docs/voice/webrtc/quickstart) also documents the 24-hour token. A 24-hour bearer is not automatically a sufficiently short-lived or least-privilege credential for this product; verify credential expiry, scopes, revocation, per-device authorization, concurrent sessions, independent inbound/outbound enforcement, and the exact current token API before implementing session issuance. The docs contain examples using more than one token endpoint, so the account-specific flow needs validation. No credentials were created and no live calls were made.
