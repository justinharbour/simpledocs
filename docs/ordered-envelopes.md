# Ordered outbound envelopes

Web and backend-connected iOS/macOS Send can put 1–10 PDFs in one envelope. The order step supports dragging or Move up/Move down. The order shown in review determines document numbers and the page order for every recipient. The direct-provider macOS edition and the older single-channel APIs are not part of this flow.

## Wire and storage contract

- Authenticated `POST /api/transmissions` uses multipart `spec` JSON and exactly one file field: one legacy `document`, ordered `documents` parts, or ordered `numberedDocuments` parts to request printed page headers. Use `numberedDocuments` even for a single PDF when headers are wanted. Don't mix fields. Using a distinct field prevents an older Worker from silently sending a subset or omitting requested headers.
- The response includes `id` (existing opaque UUID), `envelopeNumber` (six-digit string, e.g. `000001`) and `documents`, ordered by `position`. Each manifest entry is `{ position, name, pageCount, number }`; `number` is the envelope number immediately followed by the two-digit one-based position (`00000101`, `00000102`, …). One PDF with many pages still counts as one document. These are display numbers, not secrets, authorization tokens or API route identifiers.
- `GET /api/transmissions/:id` returns the same manifest; list and Records responses add `envelopeNumber`. Old records stay readable by UUID, with `envelopeNumber: null` and an empty detail manifest. They are not retroactively assigned numbers or rewritten.
- Migration `0040_ordered_envelopes.sql` allocates numbers atomically from `000001` to `999999`, across all actors using this D1 database. Allocation occurs after validation and before writing the optional cover. Legitimate gaps can result from a failed write; the sequence never wraps or reuses numbers in the live database. Exhaustion rejects new envelopes before any content is stored or deliveries are queued. Independent instances can issue the same display numbers. Back up the allocator with the rest of D1 and account for any issuance after a backup before restoring a writable instance.
- The existing `source_key` references one private packet at `outbound/<UUID>/document.pdf`. Multi-file packets use the original page order within each document. Single-file packets without headers keep their original bytes. R2 writes finish before one D1 batch commits the manifest, transmission and delivery rows. An interrupted write can leave unreferenced private objects, but never a partially committed set of deliveries. No original-object copies or individual document URLs are created. Keep the established private-object retention policy; do not expose the bucket.
- Page headers are off by default and apply to the whole packet for both fax and paper mail. Each page, including blank pages, shows only `Document <eight-digit number>`. Every page of the same source PDF uses the same number. Stamping keeps sheet dimensions and page count, and proportionally scales the artwork below a new 24-point header band instead of painting over it. File names, actors, recipient addresses and object URLs are not printed in the header. The stamped packet is private, but its printed numbers are deliberately visible to recipients.
- Fax prepends the existing recipient-specific cover when enabled. Optional `spec.fax.cover.includeNumbers: true` lists the envelope number and ordered document numbers on that cover, independently of page headers. A pre-send cover preview does not show real numbers. Paper mail uses the same ordered packet without any fax cover, and its approval hash binds the exact stored PDF bytes, including any page headers.
- V1 limits: 10 PDF parts, 5 MiB combined input and assembled PDF, and 100 document pages before any fax cover. Encrypted or unreadable PDFs are refused. Page copying also refuses common interactive features, annotations and signature containers rather than silently stripping them; supply a flattened export when copying is necessary. Copying is not sanitization, malware scanning, PDF conformance validation, or proof that output will render identically at the provider. Input limits help bound work but are not a substitute for sandboxed rendering. Existing authorized record PDF viewing remains available.
- Header stamping is deliberately narrower than plain copying. It rejects rotated, non-zero-origin, or cropped pages; nonstandard page units, sizes outside 144–1440 points on either axis, optional layers and unsupported page-level print settings; and unsupported page content stream encodings. Page drawing streams are limited to 16 MiB decoded per envelope. If the Worker cannot stamp the packet, it does not fall back to sending unstamped bytes. Re-export a flattened, unrotated PDF or explicitly turn off the option. Embedding copies drawing resources without source document or page dictionaries, but is not a tool for securely redacting source content or its resources.

## Secure email portal integration

No email behavior, routes, providers, permissions or delivery status are changed here. A future portal integration should reference the opaque transmission UUID, enforce its own recipient authorization, and treat the manifest as ordered display metadata. If reusing `source_key`, disclose that recipients will see any stamped page headers; the key references the exact outbound packet, not an unstamped copy. Do not use a six-digit number or eight-digit document number to grant access, publish an R2 key, or expose the actor-authenticated `/document` endpoint publicly. If the portal also adds a Send channel or record metadata, reconcile changes in `web/src/pages/send/index.astro`, `web/src/lib/detail.ts`, `web/worker/transmissions.mjs` and the corresponding native models; use a distinct migration number. The fax/mail queue payload and provider adapters are unchanged.
