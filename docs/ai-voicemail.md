# AI voicemail (draft; not ready for deployment)

The web phone's availability policy is independent of its connection: online or scheduled hours permit ringing only when a browser heartbeat is current. Offline bypasses ringing. Schedule times are local wall time in the configured IANA timezone; overnight intervals continue into the next day. Default is online and UTC; an empty schedule means offline. The settings editor supports one interval per day. The native apps currently have no native WebRTC softphone; they do not expose this control.

## Provider setup for a future reviewed deployment

Apply migrations `0017_ai_voicemail.sql` and `0045_sms_opt_out.sql` through the normal reviewed deployment path after confirming their allocation against all branches being integrated. Configure existing inbound Telnyx Call Control, signature verification, voicemail number, API token, greeting and R2 recording storage as described in `voice-webhooks.md`. Create a Telnyx AI assistant with an appropriate enabled model, speech recognition and voice, and set `TELNYX_AI_ASSISTANT_ID` to its ID. Set `AI_TOOL_BASE_URL` to the public HTTPS origin of this Worker, with no path. Ensure the three `/api/webhooks/telnyx/ai/*` endpoints can reach the Worker without interactive Cloudflare Access; they authenticate using per-call bearer credentials supplied to Telnyx as webhook headers. Do not log these headers, bodies, or Telnyx call-control IDs. The configured AI assistant's stored tools and instructions are overridden per call; review provider retention, subprocessors, data location and recording consent rules before use. Enter only approved facts in Settings; the knowledgebase is initially empty.

The Worker answers the unanswered caller leg with Telnyx's `assistant.id` and per-call instructions and webhook tools, allowing Telnyx to warm up before answer. Missing AI configuration uses the existing recorded voicemail flow. For a signed `call.conversation.start_failed` on an assistant-backed answer, Telnyx documents that no conversation was created and the call remains answered; the Worker starts the ordinary greeting and recording. Duplicate callbacks cannot issue duplicate greeting commands. The answer HTTP request is bounded to eight seconds and an unknown outcome is logged without caller data; this is not a bound on caller silence. The provider does not guarantee greeting readiness or bounded startup, and an ambiguous answer cannot safely be followed by a second answer or competing recording. `call.conversation.created` is not proof of audible readiness. Concurrent playback is not established as safe against assistant audio. This path has mock coverage but has not been verified with call audio.

Tools save one request of each kind per call in D1. The bearer is random per call, stored only as a digest, expires after four hours, and is bound to the `x-telnyx-call-control-id` header; duplicate identical tool calls are idempotent, conflicting duplicates are rejected. Voice events remain Ed25519-verified separately. Requests are visible to the voice owner on the Calls page and may be deleted there after the four-hour callback window, preventing replay from recreating a deleted request. Expired session credentials are cleaned by the existing scheduled Worker invocation; requests remain until deleted so unread messages are not silently lost. Clearing the knowledgebase in Settings removes its content from the current setting. D1 backups, Telnyx conversations and existing call/event logs have separate retention and deletion policies; these controls do not erase those copies. The model is instructed to disclose AI processing, avoid sensitive information, and say it does not know where knowledge is absent; these are model instructions, not a guarantee against hallucination or prompt injection.

**SMS is not sent by the agent.** It records an SMS request and the model's reported consent for owner review. On Calls, review the request, independently confirm the recipient's number and permission and check applicable opt-outs; only if confirmed may the owner choose to compose a message in Messages. Do not send if unsure. Model output is not independently verifiable consent. Signed inbound STOP events and standard STOP keywords create a durable local suppression checked at send time; START does not automatically restore permission. There is not yet an owner workflow to reconcile renewed consent and clear the local block. The local check cannot serialize against a STOP arriving after the check; provider profile-level blocking is necessary as an additional control and must be verified. Historical events, other numbers on the profile, and natural-language opt-outs may not be represented locally. There is no automatic callback or outbound call.

## Remaining blockers before merge or use

- Integrate and retest with drafts #62, #63 and #64; review migration numbering and conflicts.
- Verify Telnyx actually propagates custom authorization and call-control headers for inline tools, tests each tool's schema, and confirms call-control fallback behavior with a controlled test number after separate approval. No live test has been performed.
- Establish a retention/deletion policy covering D1 backups, existing call/event metadata, and provider-side conversations; requests otherwise remain until owner deletion.
- Establish bounded recovery for an ambiguous answer or stalled startup. Answer warm-up and explicit start-failed fallback do not guarantee that greeting audio began.
- Establish consent/opt-out enforcement before automated SMS; do not represent recorded requests as sent texts.
- Review the availability editor's one-interval-per-day limitation before editing schedules created via API with multiple intervals on the same day.

## Owner-coordinated deployment sequence

1. Before deployment, inspect the current Worker bindings and secret **names** and confirm that both `TELNYX_AI_ASSISTANT_ID` and `AI_TOOL_BASE_URL` are absent. If either is already set, do not assume deployment preserves recorded voicemail: investigate its actual value and ownership without disclosing credentials. Missing either setting makes `assistantForCall` return null, and the existing answer/greeting/record path is used. An invalid or unreachable configured assistant is not equivalent to missing configuration.
2. Reconcile migrations `0017` and `0045` against the current deployed D1 migration history and other branch allocations; back up the database and apply only through the reviewed deployment path. Preserve portal and Access configuration. Confirm the deployed Worker version and configuration without placing calls or messages.
3. Separately establish the correct Telnyx account and Simpledocs-owned assistant, its speech/model dependencies, signed voice and messaging webhooks, and profile-wide STOP blocking. Set the two AI settings only when the callback origin, Access bypass for the three authenticated tool routes, consent/retention, and provider permissions have been reviewed. Do not repurpose another product's profile.
4. The owner must decide separately whether to authorize a controlled call and SMS validation. Without those communications, callback delivery, audible startup and end-to-end suppression remain unverified; a successful deployment or passing mocked CI is not proof of provider readiness. Keep the existing recorded-voicemail configuration and an owner-approved rollback available.
